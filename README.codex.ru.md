# Paseo AIO для Codex

[English](README.codex.md) · [Исходная версия для Claude](README.ru.md)

Полный набор ролей AIO с провайдером Codex: процесс Matt Pocock, исполнители и
worktree через Paseo, Ponytail, RTK, CodeGraph и Playwright CLI. Claude для этой
версии не требуется. Исходный установщик Claude сохранён отдельно.

## Быстрый запуск

Нужны Linux, Python 3, Git, Node/npm, curl, работающий Paseo и авторизованный Codex.
Для серверных issues и PR нужен авторизованный CLI соответствующего хоста;
локальный трекер от него не зависит. Выполняйте установку от того
же пользователя ОС, под которым демон запускает Codex.

```bash
git clone https://github.com/LeonidAlekseev/paseo-aio.git
cd paseo-aio
bash install-codex.sh --with-tools --with-browser
```

Это **предварительный просмотр**: проверяется доступность моделей и выводится
список изменений. Файлы не меняются, пакеты не устанавливаются, агенты и демон
не перезапускаются. Для установки:

```bash
bash install-codex.sh --with-tools --with-browser --apply
paseo reload
```

Откройте Codex CLI от этого же пользователя и через `/hooks` проверьте и разрешите
хуки CodeGraph, RTK и Ponytail. Затем создайте **новую сессию Codex в Paseo**.
Установщик не подделывает разрешение на хуки. Если `gh` отсутствует, установите
его пакетным менеджером ОС и выполните `gh auth login`.

Для обновления только конфигов и навыков:

```bash
bash install-codex.sh --apply
```

Чтобы настроить уже установленные бинарные инструменты и установить плагины
Codex без переустановки бинарников, используйте
`bash install-codex.sh --configure-tools --apply`. Плагины могут требовать сеть.
Опция несовместима с `--with-tools` и `--with-browser`. Для отдельной установки
бинарников команда `bash codex/install-tools.sh --binaries-only --apply`
пропускает настройку Codex.

## Режимы доступа и модели

При первой установке профили используют `auto-review`. Повторная установка
сохраняет режим каждого существующего профиля из `~/.paseo/config.json`, в том
числе при обновлении описаний через `--profiles`. Чтобы явно задать режим всем
устанавливаемым профилям Codex:

```bash
bash install-codex.sh --mode full-access --apply
```

Затем `--mode` можно не указывать: выбор сохраняется при обновлениях. Режим
действует на новых агентов, запущенных с этими профилями, а не на существующие
сессии или агентов без профиля. `full-access` отключает файловый sandbox Codex.
Инструкция роли «только чтение» задаёт поведение, но не ограничивает доступ
к файловой системе средствами ОС.

Двенадцать профилей хранятся в
[codex/agent-profiles.json](codex/agent-profiles.json). Все ID начинаются с
`codex-`; профили Claude и другие пользовательские профили сохраняются.
Каждый профиль использует провайдер с тем же ID на основе `codex`, который
передаёт инструкции роли при запуске. Установщик использует имя и `notes`
профиля как инструкции: выбор ревьюера, исполнителя или исследователя задаёт
его поведение. Старые пользовательские профили с провайдером `codex` переводятся
на соответствующие провайдеры ролей.

| Профиль | Модель | Мышление | Назначение |
| --- | --- | --- | --- |
| codex-orchestrator | Astra | high | План, делегирование, интеграция |
| codex-implementer-heavy | Astra | high | Архитектура, миграции, большой рефакторинг |
| codex-implementer-medium | Sol | medium | Фичи, баги, UI, исправления после ревью |
| codex-implementer-light | Sol | medium | Небольшие локальные изменения |
| codex-implementer-trivial | Sol | low | Механические изменения |
| codex-merger | Sol | medium | Последовательное слияние тикетов |
| codex-reviewer | Astra | high | Standards / Spec review |
| codex-code-research | Sol | medium | Исследование кода |
| codex-web-research | Sol | medium | Документация и API с источниками |
| codex-images | Sol | medium | Ассеты при наличии инструмента генерации |
| codex-advisor | Astra | high | Независимое мнение по архитектуре |
| codex-arbiter | Astra | high | Спорные замечания ревью |

Astra — `gpt-6-astra`, Sol — `gpt-6.1-sol`. Astra назначена исходным ролям
Opus 5.5 (оркестратор и тяжёлый исполнитель), а также ревьюеру, архитектурному
советнику и арбитру. Модель и уровень мышления проверяются по живому каталогу
Codex либо явно настроенному каталогу роли. Можно редактировать JSON по ролям
или переопределить все роли флагами `--model MODEL --thinking EFFORT`. Недоступная
модель вызывает ошибку, а не скрытую замену. По умолчанию advisor — ещё один
независимый проход того же семейства моделей. Профиль `images` не создаёт
инструмент генерации изображений; его наличие нужно проверить в самой сессии.

Отсутствующие у провайдера роли поля `models` и `additionalModels` копируются
из `codex`; собственные настройки роли, включая пустые списки, сохраняются.
Если динамический каталог роли нельзя проверить по живому базовому каталогу
(например, из-за другого окружения или удаления базовых переопределений моделей),
установка останавливается до записи конфигов. В таком случае задайте этому
провайдеру явный непустой список `models` с `thinkingOptions`. Проверка каталога
не доказывает, что учётная запись сможет успешно запустить модель.

## Работа в проекте

Создайте управляемого агента в Paseo и выберите **Profiles → Codex · Orchestrator**.
Провайдер автоматически предписывает использовать `codex-orchestrate` и
`codex-pocock-paseo` для задач разработки. Можно сразу писать задачу без названий
навыков. Для первоначальной настройки проекта:

```text
Настрой этот репозиторий для оркестрации через Paseo.
Сначала покажи трекер, целевую ветку и проверки, которые предлагаешь.
```

Координатор находит установленные навыки Pocock по каталогу Codex, а роли запускает
через `codex-pocock-paseo` и MCP Paseo. Исполнитель получает отдельный worktree,
scope и проверки. Максимум три пишущих агента и два ревьюера/исследователя;
изменения одних файлов и слияния в integration выполняются последовательно.

Явное согласие, уже данное на scope, сохраняется. `dev` — соглашение исходного
AIO, а не ветка, которую установщик создаёт в любом репозитории. Целевую ветку
определяют инструкции проекта и пользователь. Push, публикация PR, merge и релиз
выполняются только в согласованных границах задачи. Роль «только чтение» в prompt
сама по себе не является файловым sandbox.

Инструкции роли действуют при создании нового агента с выбранным профилем.
Применение настроек модели к существующему обычному Codex-агенту не меняет
провайдер запуска. Координатор по-прежнему передаёт scope, рабочее пространство,
проверки и критерии приёмки конкретной задачи.
Это инструкции запуска по умолчанию. Пользовательский `systemPrompt` сессии
или `daemon.appendSystemPrompt` в Paseo может их переопределить; включите нужную
роль в эту инструкцию и проверьте её в новой сессии.

## Если серверные issues недоступны

Инструкции Codex переключают задачи на локальный Markdown, если issues отключены,
нет нужных прав, авторизации/CLI или выбранного трекера. Агент сообщает причину,
фиксирует локальный режим в `docs/agents/issue-tracker.md` и продолжает согласованную
работу. Включать issues или расширять права для этого не требуется. Явно выбранный
локальный режим сохраняется; появление доступа не переносит задачи обратно автоматически.

```text
.scratch/<feature>/spec.md
.scratch/<feature>/issues/01-<ticket>.md
.scratch/<feature>/issues/02-<ticket>.md
```

В тикетах — Status, Blocked by, scope, проверки и комментарии. Координатор ведёт
файлы в основном checkout и передаёт исполнителям доступные ссылки: незакоммиченные
задачи сами в worktree не появятся. Для существующих серверных задач сохраняются
исходные ссылки. При неизвестном результате отправки агент сначала выясняет исход,
чтобы не создать дубликат. Код и разрешённые PR могут по-прежнему находиться в Gitea
или другом Git-хостинге.

Общее [правило трекера](codex/skills/codex-orchestrate/references/issue-tracker.md)
устанавливается вместе с навыком и действует также при прямом вызове навыков Pocock.
Оно описывает статусы, зависимости, завершение задач и сохранение истории. Это
инструкция агенту, а не фоновая служба синхронизации.

## Что устанавливается

- Навыки `codex-orchestrate` и `codex-pocock-paseo` в `~/.agents/skills`.
- Отсутствующие встроенные навыки Paseo вместе с Apache-лицензией. Уже имеющиеся
  копии не заменяются. Это снимок; используйте схемы инструментов текущего Paseo.
- Блок в `~/.codex/AGENTS.md`, ограниченный маркерами. Остальной текст сохраняется.
  Непустой `AGENTS.override.md` вызывает понятную ошибку, поскольку скрывает этот файл.
- Хук `SessionStart` в `~/.codex/hooks.json` с сохранением других обработчиков.
  Он асинхронно индексирует новые worktree через CodeGraph. Блокировка предотвращает
  одновременную индексацию одного worktree. Индексы разных веток не копируются.
  Пока индекс не готов или при ошибке агент использует rg/read.
- `~/.codex/rules/paseo-aio.rules`: запреты распространённых разрушительных Git-команд,
  включая некоторые формы RTK. Это префиксные правила, не полный анализатор shell.
  Для `main`/`dev` всё равно нужна серверная защита веток; в Full Access нельзя
  считать эти правила полноценной границей безопасности.
- В `~/.paseo/config.json` — профили `codex-*`, включение MCP-инъекции и
  базовый провайдер, название и команда запуска каждой роли. Команда использует
  настроенный бинарник Codex и добавляет `developer_instructions` для роли.
  Адрес, relay, CORS, ключи, терминалы, переключатели провайдеров, браузер и
  автоархивация сохраняют прежние настройки.

Поддерживаются существующие `CODEX_HOME` и `PASEO_HOME`. Для подготовки конфигов
есть `--codex-home`, `--skills-dir`, `--paseo-home`, `--profiles`. `--offline`
пропускает проверку моделей только при просмотре; применять неподтверждённые модели
этим флагом нельзя.

Изменяемые файлы сохраняются в приватный каталог
`~/.codex/backups/paseo-aio/<timestamp>` с `manifest.json`: исходный путь, резервная
копия и права. Запись каждого файла атомарна; при ошибке записи ранее изменённые
файлы этого шага восстанавливаются. Повторная установка тех же конфигов ничего
не меняет.

Установка сторонних пакетов **не транзакционная**: при сбое часть пакетов может
остаться установленной. Перед ней копируются `config.toml`, `hooks.json` и
`AGENTS.md` в `~/.codex/backups/paseo-aio-tools`. Ошибки не скрываются.

Для отката проверьте manifest, восстановите нужные файлы и выполните `paseo reload`.
`backup: null` означает новый файл. Не затирайте изменения, сделанные после установки,
старой копией. Удаление npm-пакетов и плагинов выполняется отдельно.

## Инструменты и плагины

`--with-tools` устанавливает CodeGraph 1.6.2, RTK 1.1.0, Playwright CLI 0.1.23,
нативные плагины Matt Pocock и Ponytail для Codex. Версии и Git-ревизии закреплены
в [install-tools.sh](codex/install-tools.sh). RTK проверяет checksum загрузки.
Для Ponytail используется локальный marketplace в `$CODEX_HOME/marketplaces/paseo-aio-ponytail`
(по умолчанию `~/.codex/marketplaces/paseo-aio-ponytail`), который закрепляет Git-ревизию
самого плагина вместо ссылки на `main` из исходного marketplace.
Существующая регистрация исходного marketplace Ponytail заменяется автоматически;
идентификатор плагина `ponytail@ponytail` сохраняется.
Навыки Playwright ставятся с `--skills=agents`, а Chromium — версии, соответствующей
точной зависимости CLI. `--with-browser` также устанавливает библиотеки ОС и может
потребовать root/sudo. Обновление плагинов вне этого установщика может изменить
закреплённые снимки. Настройка браузера создаёт `~/.playwright/cli.config.json`,
если его ещё нет, и выбирает загруженный Chromium для `playwright-cli open`.
Существующий выбор сохраняется; для отдельного запуска используйте
`--browser=chromium`.

Пять дополнительных плагинов интерфейса/автоматизации Paseo из исходного AIO
не обязательны. Для явной установки на демон:

```bash
while IFS= read -r plugin; do
  paseo plugin install "$plugin" || break
done < paseo/plugins.txt
```

Эти плагины выполняются без sandbox; версии реестра здесь не закреплены и их
совместная работа с Codex-портом не проверена. Основной процесс от них не зависит.

## Проверка перед использованием

```bash
python3 -m unittest discover -s tests -v
bash -n install-codex.sh codex/install-tools.sh
codex execpolicy check --rules codex/paseo-aio.rules -- git reset --hard HEAD
bash install-codex.sh
```

Обычный CI проверяет синтаксис shell и тесты на временных данных без загрузки
пакетов и работающего демона. Тесты проверяют сохранение настроек, роли при
запуске, повторную установку, backup/rollback, отказ на недоступной модели,
предварительный просмотр и обработку ошибок/конкуренции индексатора.
Дополнительный тест RTK использует `--dry-run`, если CLI установлен.

Живой preview, проверка схемы Paseo и аргументов запуска Codex требуют
установленных инструментов; preview не применяет конфигурацию. Установка пакетов,
разрешение хуков и полный цикл делегирования требуют отдельной проверки в тестовом
окружении. В отдельном проекте проверьте обнаружение навыков, разрешённые хуки,
MCP Paseo, исполнителя в своём worktree, индексацию, проверки проекта и ревью.
Не используйте production-ветки для пробных merge и push.
